# 工位级预约细化设计说明（双粒度资源模型）

> 版本：v3.0　日期：2026-10-24
> 适用项目：高校实验室智能预约与排期系统（Spring Boot + Vue + 微信小程序）
> 关联文档：`doc/系统分析与设计说明书.md`、`doc/UML图集说明.md`
> 本文回答的需求：少数人员使用实验室时，不必独占整间实验室，可按工位预约；有效固定预约直接生效。

---

## 1 需求背景与目标

### 1.1 原始模型的问题

整室预约以“实验室 × 时段”为最小资源单位，小组只使用少量工位时也会排除其他申请人，造成空间闲置。工位化的目标是让整室与工位两种预约在同一套规则下**双向互斥、独立审计、可安全释放**。

### 1.2 设计目标

1. 支持整室与工位两种预约粒度，保留教师整室教学预约。
2. 使用固定 48 位掩码和现有 Java、MySQL、Redis 技术栈，不引入超宽位运算。
3. 任一预约方向都不得覆盖另一粒度的有效占用。
4. 固定预约、取消、爽约、提前签退和自动发布均有明确事务与状态边界。
5. 排期算法在同一资源快照上比较，生产主方案与实验对照结果分离。

## 2 关键设计决策

### 决策 1：整室与工位共存，而不是相互转换

预约单包含 `reservation_mode ∈ {ROOM, SEAT}` 和 `seat_count`。整室请求服务教学等需要独占空间的场景；工位请求只占用实际分配的 K 个工位，其他工位仍可预约。

整室预约使用独立的整室掩码表达独占规则；工位预约使用每工位独立掩码表达具体座位占用。

### 决策 2：实验室日位图与工位日位图分表

- `t_slot_bitmap(lab_id, date, mask, version)`：每实验室每天一行，记录整室占用。
- `t_seat_bitmap(seat_id, date, mask, version)`：每工位每天一行，记录该工位占用。
- 两个 `mask` 均为 `BIGINT UNSIGNED`，只使用低 48 位；Java 使用 `long` 完成位运算。

每个字段的位运算都处于 MySQL 64 位范围内，座位增加不需要改变表结构，释放也能明确定位到具体工位。

代价是行数随实际发生占用的“工位—日期组合”增长：

`工位位图行数 = 有有效或历史占用的不同 (seat_id, date) 组合数`

索引和行开销以实际 DDL 与测试数据测量为准，不使用未经测量的固定容量结论。

### 决策 3：惰性建行与统一空值语义

尚未发生相关操作时，可以不创建位图行；查询无行一律按 `mask = 0L` 处理。固定预约或自动发布首次操作某实验室日期时，先插入整室零掩码行；若并发插入发生唯一键冲突，则读取既有行继续事务。

整室零掩码行还作为该实验室日期的数据库行锁锚点。工位行只在首次工位占用时创建，取消后零掩码行可以保留，不影响“无行等于零”的读取规则。

### 决策 4：固定预约直接正式分配

固定工位预约在提交事务中直接写入：

- 状态为已通过的预约单；
- K 条 `t_reservation_seat` 正式座位分配；
- 对应工位位图；
- 初始状态日志。

任一步失败均整体回滚，不出现预约已经生效但座位不完整的中间状态。系统可靠性不变量是：**已通过工位预约必须具有完整、有效的正式座位分配**。

### 决策 5：固定时空与可调度需求分流

`allocation_mode = FIXED` 的申请在提交事务成功后生效；`allocation_mode = SCHEDULABLE` 的需求提交时不占位，进入待排期。

定时任务对三套算法分别建任务并共享快照，只有配置指定的主算法合格方案会重检并发布，其他结果仅用于实验对照。主方案未解决失败时，需求保留待排期进入后续批次，超过期望使用期限转为已过期。

## 3 领域模型与数据结构

### 3.1 关键对象

| 对象 | 关键属性 | 职责 |
|---|---|---|
| 工位 | seatId、labId、seatCode、区域、配置等级、靠窗标记、状态 | 判断档案状态、硬配置和软偏好 |
| 实验室时段位图 | labId、date、mask、version | 整室冲突检测及实验室日期行锁锚点 |
| 工位时段位图 | seatId、date、mask、version | 具体工位冲突检测、占用与释放 |
| 座位分配 | resvId、seatId、timeMask、分配方式 | 固定提交或自动发布后的正式座位归属 |
| 预约申请 | allocationMode、reservationMode、起止时间、状态、签到渠道 | 驱动固定预约、可调度需求和状态迁移 |
| 签到终端 | deviceId、labId、terminalCode、密钥哈希、状态 | 验证实验室电脑签到渠道 |

### 3.2 工位及占用表

`t_lab_seat` 至少包含：`seat_id`、`lab_id`、`seat_code`、`zone_code`、`seat_index`、`spec_level`、`near_window`、`seat_status`。实验室内使用连续、稳定的 `seat_index` 排序，不使用全局自增 ID 推导物理位置。

约束与索引：

- `uk(lab_id, seat_code)`：实验室内工位编号唯一。
- `uk(lab_id, seat_index)`：实验室内排序号唯一。
- `idx(lab_id, seat_status)`：查询可用工位。
- `t_seat_bitmap.uk(seat_id, date)`：工位日位图唯一。
- `t_reservation_seat.uk(resv_id, seat_id)`：防止同一预约重复分配同一座位。

`time_mask` 表示该预约在该工位上实际占用的时间片，释放时必须与当前预约及有效分配记录核对，不能只凭一个脱离业务单据的掩码清位。

### 3.3 与全量数据模型的关系

本细化设计与主说明书中的 `t_reservation_batch`、`t_credit_record`、`t_appeal` 等共同形成 23 表数据模型。完整字段、关系和索引以 `doc/系统分析与设计说明书.md` §4.5 及图 4-6 为准。

## 4 双向冲突检测与落座

### 4.1 判定规则

设申请时间掩码为 `Q`，整室掩码为 `R`，工位 i 的掩码为 `S[i]`。

**工位申请：**

1. `(Q & R) != 0`：整室占用，直接冲突。
2. 过滤维修、停用及不满足硬配置要求的工位。
3. 对每个候选工位要求 `(Q & S[i]) == 0`。
4. 可用候选不足 K 个时返回冲突，不先写部分分配。

**整室申请：**

`U = R OR S[0] OR ... OR S[m-1]`，仅当 `(Q & U) == 0` 时允许占用。

因此，“已有整室后约工位”和“已有工位后约整室”都会被拒绝。自动发布也执行同样的双向检测，但只处理尚未占用的 SCHEDULABLE 需求，不把它们自身误判为冲突。

### 4.2 参考伪代码

```java
long roomMask = queryRoomMask(labId, date);
List<SeatMask> occupied = querySeatMasks(labId, date);

if (request.isRoom()) {
    long unionMask = roomMask;
    for (SeatMask seat : occupied) unionMask |= seat.mask();
    require((request.timeMask() & unionMask) == 0L, CONFLICT);
} else {
    require((request.timeMask() & roomMask) == 0L, CONFLICT);
    List<Seat> candidates = seatCatalog.findActive(request.labId()).stream()
        .filter(seat -> seat.meetsHardRequirement(request))
        .filter(seat -> (request.timeMask() & occupied.maskOf(seat.id())) == 0L)
        .toList();
    List<Seat> chosen = seatAllocator.allocate(candidates, request);
    require(chosen.size() == request.seatCount(), CONFLICT);
}
```

单个 48 位掩码运算为 O(1)；全工位并集和候选过滤为 O(m)。一次数据库查询可以减少往返次数，但不会消除 m 个工位的计算。

### 4.3 落座算法

1. 过滤状态不可用、硬配置不满足或时间冲突的工位。
2. 按区域、`seat_index` 及偏好分组排序。
3. 优先选取同区域连续且满足软偏好的 K 个工位。
4. 无完整连续段时，按配置满足度、靠窗偏好、工位编号选取 K 个，并记录未满足的软偏好。
5. 候选不足 K 个则整个请求不分配，不保留部分结果。

复杂度为 O(m log m + K)，其中排序是主要成本。工位偏好错配率只统计软偏好未满足情况；硬约束不满足直接视为分配失败。

## 5 并发控制与事务

### 5.1 统一实验室日期边界

所有影响某实验室某日占用的操作共用：

`resv:lab:{labId}:{date}`

整室、工位、取消、爽约、提前签退和自动发布均遵循该边界。Redis 锁使用唯一持有者令牌，并通过 Lua 按令牌释放；批量操作按 `labId、date` 排序获取锁。

Redis 锁用于减少竞争，不作为唯一正确性来源。数据库事务内还需锁定对应整室日位图行，使两个粒度在数据库层遵循同一互斥点。

### 5.2 固定工位预约提交事务

1. 获取实验室日期锁。
2. 开启数据库事务，确保并 `FOR UPDATE` 锁定整室日位图行。
3. 读取整室和候选工位最新掩码，完成双向检测与 K 个工位选择。
4. 插入已通过预约单及 K 条正式座位分配。
5. 对每个工位执行带版本和冲突条件的位图更新。
6. 写入初始状态日志并提交事务；任一步失败则回滚全部写入。
7. 在 `finally` 中释放 Redis 锁。

```sql
UPDATE t_seat_bitmap
   SET mask = mask | ?, version = version + 1
 WHERE seat_id = ? AND date = ? AND version = ?
   AND (mask & ?) = 0;
```

参数分别为申请掩码、工位、日期、旧版本和同一申请掩码。影响行数不是 1 时，当前事务回滚后重新读取，不在部分写入尚未回滚时重试。

整室位图使用相同的版本与冲突条件思路。`BIGINT UNSIGNED` 只保存低 48 位，位运算不会超出 MySQL 64 位范围。

### 5.3 自动发布事务

- 只有主算法任务且第二阶段无未解决失败的方案可进入发布。
- 按 `labId、date` 顺序加锁，事务内锁定整室日行并重新读取最新占用。
- 对主方案执行双向检测和落座复核；快照过期、冲突或分配失败则回滚。
- 成功后更新结果发布标记、预约为已通过、正式座位分配、位图和状态日志，并一次性提交。
- 对照任务只保存候选结果和实验指标，不占用任何资源。
- 主方案发布失败时，需求保留待排期并进入后续批次；超过期望使用期限转为已过期。

落座失败率用于监测“已通过固定工位预约是否具有完整正式分配”这一不变量，不替代事务和异常测试。

### 5.4 释放与历史统计

| 场景 | 资源处理 | 历史处理 |
|---|---|---|
| 开始前取消 | 释放该预约尚未开始的全部占用 | 保留预约与状态日志 |
| 爽约、违规终止 | 释放当前之后的剩余占用 | 保留违规与信用流水 |
| 提前签退 | 只释放当前之后尚未开始的完整时间片 | 保留已使用部分和签到签退时间 |
| 正常结束 | 保留已使用时间片的占用事实 | 以预约及签到签退明细统计实际使用 |

释放前必须校验预约当前状态、原正式分配记录和 `time_mask`，并使用原状态条件更新保证幂等。位图不是唯一历史事实源，实际利用率不得仅根据已经释放的位图反推。

## 6 完整生命周期

```text
固定工位预约
  提交 → 双向检测 → 选择 K 个工位
       → 已通过预约 + 正式分配 + 位图 + 日志同事务
       → 签到窗口内扫码或电脑账号签到 → 使用中
       → 签退或到时自动结束 → 已完成

已通过
  ├─ 按规则取消 → 已取消（迟到取消同时登记违规）
  └─ 超过签到宽限仍未签到 → 爽约 → 释放剩余占用并记录信用流水

可调度需求
  提交（不占位）→ 待排期 → 主方案自动重检并发布 → 已通过
                     ├─ 取消 → 已取消
                     ├─ 本批发布失败 → 保留待排期进入后续批次
                     └─ 超过期望使用期限 → 已过期
```

两种签到渠道只负责采集凭证，最终均由后端校验身份、本人预约、实验室和签到窗口。预约已处于使用中时，重复签到不生成新的签到事实。

## 7 两阶段排期与实验指标

### 7.1 两阶段分配与主方案

1. 第一阶段：三套引擎只处理 SCHEDULABLE 需求，在包含固定占用和资源状态的快照上分配实验室与时段。
2. 第二阶段：对工位需求执行统一落座算法，计算实际分配和软偏好满足情况。
3. 主算法由配置指定；只有主任务的合格方案进入自动发布。
4. 其他算法任务只保存候选结果和实验指标，不参与生产占用。
5. 主任务存在未解决失败或发布重检失败时，需求保留待排期进入后续批次。

遗传算法第一阶段适应度使用预计分配成功率、预计资源利用率、时间碎片和约束违反惩罚，不引用第二阶段尚未产生的实际偏好错配结果。最终五项指标由 Evaluator 在第二阶段后统一计算。

### 7.2 指标口径

| 类型 | 指标 | 说明 |
|---|---|---|
| 算法对比 | 分配成功率 | 最终成功分配并落座的请求占比 |
| 算法对比 | 平均工位利用率 | 已分配工位时间片占可用工位时间片比例；整室按占用全部可用工位计 |
| 算法对比 | 工位偏好错配率 | 未满足软偏好的已分配工位数 / 已分配工位总数 |
| 算法对比 | 时间碎片率 | 不能组成最小预约时长的空闲片 / 总空闲片 |
| 算法对比 | 两阶段求解耗时 | 分阶段记录并给出总耗时 |
| 系统可靠性 | 落座失败率 | 已通过固定工位预约中缺少有效正式分配的预约占比 |

### 7.3 实验留存

四组请求规模 N = 50 / 100 / 200 / 400，同时记录工位资源数、请求时长与偏好分布。整室与工位需求约按 3:7 混合，三套算法共享快照和第二阶段策略。

GA 使用至少 10 个独立随机种子并报告均值、标准差；确定性算法的质量指标单次计算。每次任务保存数据集编号、需求/资源快照、参数、随机种子、重复序号和运行环境，避免只保存结果而无法重建输入。

## 9 验收标准

1. **整室后约工位**：同时段工位申请被拒绝，整室占用不变。
2. **工位后约整室**：任一有效工位占用都会阻止同时段整室申请。
3. **固定工位预约直接生效**：合法申请通过后，预约为已通过且具有 K 条完整正式分配。
4. **并发容量**：100 个请求争抢同一时段 20 个工位，成功数不超过 20，无重复分配和孤儿记录。
5. **事务回滚**：任一多表写入步骤失败，预约单、位图、正式分配和日志均不产生部分提交。
6. **释放幂等**：取消、爽约和提前签退按剩余时间规则释放，重复任务不影响后续有效预约。
7. **惰性建行**：无行与零掩码查询结果一致；工位数量增加不需要新增掩码列。
8. **批量提交**：全部可用时整批生效，任一冲突时整批回滚，不保留部分批次。
9. **自动发布**：只有主算法合格方案占用资源，对照任务无占用；失败保留待排期。
10. **统一签到**：小程序扫码和电脑账号签到均要求本人、同实验室、已通过预约和有效时间窗。
11. **终端安全**：错误密码、错误终端、无预约及连续失败均按规则拒绝，不记录敏感日志或保留完整学生会话。
12. **实验可比可复现**：五项算法指标完整，可靠性指标单列，快照、参数、随机种子和运行环境可追溯。

## 10 智能助手与工位数据边界

独立 FastAPI + LangChain 智能助手只能通过 Spring Boot 的白名单只读接口获取实验室、工位、规则和当前用户预约信息，不得直连工位表、位图表或预约表，也不得通过模型直接执行占用、释放、签到或排期发布。

智能助手返回的空闲信息必须附带数据时间，仅用于解释和生成预约草稿。草稿默认 `allocationMode = FIXED`，其中的实验室、时段、预约粒度、工位数量和偏好经 Pydantic 校验后，只能回填普通预约表单；用户确认后仍按本文 §4、§5 执行双向冲突检测、落座和事务写入，模型输出不构成资源占用事实。

对话历史按 `userId + threadId` 存于 Redis 并设置过期时间与最大消息数，不新增工位或对话关系表。模型不可用、工具越权或输出无效时，普通工位预约继续使用，不降级为绕过校验的直接写入。
