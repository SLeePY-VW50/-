## 1 可行性研究与计划

### 1.1 技术可行性

| 维度 | 选型 | 可行性说明 |
|---|---|---|

| Web 端 | Vue 3 + Element Plus + ECharts | 支撑教师、系统管理员及实验室管理员只读页面 |

### 1.3 经济可行性

系统主要采用开源组件，可复用学院服务器、实验室电脑和现有微信主体。新增成本主要是小程序主体维护、域名与证书、模型调用、开发测试和运维；若暂时缺少正式主体或模型凭据，先以开发版和接口模拟数据验证，不将正式发布成本表述为零。

### 1.4 操作可行性

- 学生：在微信小程序完成查询、预约、取消、扫码签到和签退，也可在实验室电脑通过学号与密码签到，或通过智能助手进行规则问答和生成预约草稿。
- 教师：通过 Web 完成单个或批量教学预约，并查看个人使用统计。
- 实验室管理员：仅查看预约、使用、排期结果和统计，不执行资源或状态变更。
- 系统管理员：负责用户权限、资源规则、终端维护、违规处理与申诉核定。
- 定时任务：自动执行排期、主方案发布、爽约判定、到时结束和日统计。
- FastAPI 智能助手服务：通过 Spring Boot 只读接口获取必要数据，生成回答和预约草稿；服务不可用时普通预约与签到继续使用。

## 2 用例分析

系统功能模块见 **图 2-1（`uml/feasibility/02_function_modules.puml`）**，包括预约业务、使用与信用、资源规则、智能排期、统计分析、系统管理、移动签到渠道及智能助手。

**图 3-1（`uml/system-analysis/01_use_case.puml`）** 给出用例视图，共 **20 个用例、6 个用例包、5 类参与者**。

### 2.1 参与者

| 参与者 | 职责 | 主要用例 |
|---|---|---|
| 学生 | 移动预约与使用 | 微信绑定、查询、提交/取消预约、两种签到、签退、信用与申诉、智能问答与预约草稿 |
| 任课教师 | 教学与批量预约 | 查询、单个/批量申请、可调度需求、签到签退、统计查看 |
| 实验室管理员 | 只读使用查看 | 查看预约使用、排期结果、利用率与统计报表 |
| 系统管理员 | 平台与规则管理 | 用户权限、资源规则、签到终端、违规处理、申诉核定、备份恢复 |
| 定时排期任务（系统时钟） | 自动触发 | 排期与主方案发布、爽约判定；到时结束与日统计为系统内部职责，不单列外部用例 |

### 2.2 关键用例规约：提交预约（UC02）

| 项 | 内容 |
|---|---|
| 主参与者 | 学生 / 任课教师 |
| 前置条件 | 已通过所需渠道登录；信用分 ≥ 60；实验室及所需工位可用 |
| 业务输入 | `allocation_mode`（FIXED / SCHEDULABLE）、预约粒度、日期时段、人数、用途及工位偏好 |
| 固定时空主场景 | 校验参数 → 获取实验室日期锁 → 数据库事务与整室日行锁 → 双向冲突检测 → 写已通过预约、正式工位分配、位图和日志 → 提交事务后释放锁 |
| 可调度主场景 | 校验需求与偏好 → 写入预约单（待排期）→ 不占资源 → 由定时任务处理 |
| 扩展场景 | 锁获取失败则提示稍后重试；冲突则返回冲突时段；任一写入失败则回滚全部内容；可调度需求在期限前未发布可进入后续批次 |
| 后置条件 | FIXED 为已通过且占用与座位分配完整；SCHEDULABLE 为待排期且无占用；不得出现部分写入 |
| 业务规则 | 30 分钟粒度；单次 0.5–4 小时；默认提前 1–14 天；同一用户同一时段仅允许一条有效预约 |

### 2.3 关键用例规约：签到（UC04）

| 项 | 微信小程序扫码签到 | 实验室电脑账号签到 |
|---|---|---|
| 前置条件 | 微信已与学号绑定；存在本人已通过预约 | 学生账号存在、未停用并与本人学号关联；签到电脑与实验室绑定且终端有效；存在本人已通过预约 |
| 操作 | 调用 `wx.scanCode` 扫描实验室签名二维码，选择或确认预约 | 在签到专用页输入学号和密码，必要时选择预约 |
| 系统校验 | 登录身份、二维码签名、预约归属、实验室、状态及签到窗口 | 终端会话、学号密码、账号有效状态、预约归属、实验室、状态及签到窗口 |
| 成功结果 | 条件迁移已通过→使用中，记录签到时间和渠道并写状态日志 | 与扫码签到共用同一状态迁移和日志口径 |
| 异常处理 | 二维码无效、非本人预约、实验室不匹配、时间不符均不迁移 | 密码错误、终端不匹配、无有效预约、时间不符均不迁移；连续失败触发限次或短时锁定 |
| 重复操作 | 已处于使用中的预约按已签到处理，不重复生成签到事实或日志 | 同左 |

签到窗口统一为 `[开始时间 - 15 分钟, 开始时间 + 15 分钟]`。电脑签到只依赖有效的本人学号账号，不要求先完成微信绑定。电脑认证成功若只有一条可用预约则直接签到；若有多条，只发放有效期 2 分钟、仅限本次签到的选择凭证，选定后立即失效。认证或签到结束后清除密码输入，不建立完整个人中心会话。

### 2.4 其他核心用例规约

| 用例 | 核心规则 | 异常与结果 |
|---|---|---|
| UC03 取消预约 | 待排期、已通过均可按规则取消；开始前不足 2 小时取消仍进入已取消，但生成违规记录 | 条件更新原状态，释放剩余占用并写日志；重复取消保持幂等 |
| UC06 绑定微信与学号 | 后端通过 `wx.login` 凭证获得 openid，再验证现有学号和密码并建立唯一绑定 | 学号或密码错误、账号停用、openid 已绑定其他账号均失败，不写敏感日志 |
| UC07 查看预约与使用记录 | 实验室管理员只有只读权限，可按实验室、日期和状态筛选 | 不提供任何状态修改或资源维护入口 |
| UC09 申诉与信用恢复 | 学生/教师提交申诉，系统管理员核定 | 成立时撤销违规并追加恢复流水，历史不抹除 |
| UC13 自动排期 | 定时任务仅读取 SCHEDULABLE 需求；三套算法各自任务共享快照 | 主算法合格方案自动重检发布，其余仅实验；失败保留待排期并记录原因 |
| UC15 查看排期与分配结果 | 实验室管理员和系统管理员可查看任务、指标与分配明细 | 仅查询，不提供任何修改入口 |
| UC20 智能预约问答与草稿 | 学生通过白名单只读工具查询规则、空闲和本人预约，AI 生成回答或预约草稿 | 模型失败则回退普通表单；草稿经 Pydantic 校验和用户确认后才进入既有预约接口 |

教师批量申请采用“一个批次、多条整室预约明细”。一个批次包含同一实验室的多个连续或不连续时段；提交时整批校验和占位，全部成功才生成批次及已通过明细，任一失败则整批回滚。

### 2.5 非功能需求与验收目标

以下是**设计验收目标**，不是已有实测结果；测试环境与结果须另行记录。

| 类别 | 目标 |
|---|---|
| 并发正确性 | 100 个请求争抢同一时段 20 个工位时，成功数不超过 20；两种粒度先后次序均不得重复占用 |
| 性能 | 在记录的测试环境下，100 并发固定预约 P95 响应时间目标小于 2 秒；排期与发布异步执行 |
| 权限隔离 | 实验室管理员所有写接口均不可调用；系统管理员接口执行 RBAC；学生只能操作本人数据 |
| 凭据安全 | 密码使用 BCrypt 校验；HTTPS 传输；密码、AppSecret、终端密钥不写日志且不以明文保存 |
| 公共终端安全 | 签到不建立完整学生会话；签到选择凭证限时且一次性；成功或超时后清除表单与短期凭证 |
| AI 权限与隐私 | AI 仅调用白名单只读工具，不直连业务数据库；会话按用户隔离；不向模型发送密码、openid、手机号和完整信用记录 |
| AI 可用性 | 模型超时、限流或输出无效时回退普通预约表单，不影响固定预约、签到和自动排期；草稿必须经用户再次确认 |
| 可靠性 | 多表写入失败无孤儿占用；每日备份，目标 RPO ≤ 24 小时、RTO ≤ 4 小时，并执行恢复演练 |
| 可审计性 | 状态、信用、申诉、签到渠道和自动发布均持久化，关键业务日志覆盖率为 100% |
| 可复现性 | 算法实验保存数据集、资源快照、参数、随机种子、重复序号及运行环境；AI 调用记录模型、参数、耗时和 token 用量但不记录敏感正文 |

### 3.2 分析阶段的关键抽象决策

1. **固定 48 位掩码**：每个实验室或工位每天使用一个掩码，单次运算为 O(1)，全工位筛选按 O(m) 描述。
2. **整室与工位双向互斥**：两个预约方向在同一并发边界内检查，任何一方都不能覆盖另一方。
3. **固定预约直接生效**：有效请求在一个事务内完成预约、正式分配和位图写入，减少中间状态。
4. **固定与可调度需求分流**：前者提交时生效，后者由定时任务发布主方案时生效。
5. **生产排期与算法对照分离**：主算法结果用于自动发布，其他算法只产生同快照的实验数据。
6. **签到渠道与业务规则分离**：微信小程序和实验室电脑只负责采集凭证，最终签到由同一后端服务判定。
7. **业务明细是历史事实源**：预约、签到签退、信用与状态日志用于审计和统计，位图服务于冲突检测。
8. **智能助手与业务核心分离**：FastAPI 仅通过 Spring Boot 白名单只读接口获取数据；预约草稿必须经过用户确认和既有事务校验，模型不参与业务事实判定。

### 4.3 状态模型设计

**图 4-4（`uml/oo-design/07_state_reservation.puml`）** 定义预约生命周期：

```text
FIXED：校验与占位成功 → 已通过 → 使用中 → 已完成
SCHEDULABLE：提交（不占位） → 待排期 → 自动发布 → 已通过

待排期 → 已取消 / 已过期
已通过 → 已取消 / 爽约
使用中 → 已完成 / 违规终止
```

- 签到窗口为 `[开始时间 - 15 分钟, 开始时间 + 15 分钟]`；超过后仍无签到记录才判定爽约。
- 开始前不足 2 小时取消仍进入已取消，同时登记违规并释放剩余占用。
- 待排期超过期望使用期限转为已过期；所有状态迁移使用原状态条件更新并写入 `t_reservation_log`。
- 信用变动、正式座位分配和自动发布是业务动作，不另设为预约状态。
- 正常结束保留已使用事实；提前签退只释放当前之后尚未开始的完整时间片，实际使用统计以签到签退明细为准。

**核心表职责**

- `sys_user`：在既有账号字段上增加可空唯一的 `wechat_openid` 和 `wechat_bind_time`，一个微信身份只能绑定一个学号账号。

- `t_slot_bitmap`：每实验室每天一行整室 48 位掩码；`uk(lab_id, date)`，同时作为数据库行锁锚点。

- `t_reservation_seat`：固定预约提交或主方案发布时直接写入正式分配，保存 `time_mask` 与分配方式。
- `t_credit_record`：只追加信用变动；用户信用分更新与记录写入同事务。
- `t_appeal`：关联违规记录，保存申请、核定状态与意见；每个违规记录最多一条申诉。
- `t_schedule_task`：保存算法、主任务标记、需求/资源快照、参数、随机种子、重复序号、运行环境和任务状态。
- `t_schedule_result`：保存候选实验室、时段、候选工位 JSON、发布标记与发布时间；同一任务中每个申请最多一条结果。
- `t_algorithm_experiment`：通过唯一 `task_id` 保存一次运行的五项指标和分阶段耗时。

**AI 对话的非关系型存储**：对话不新增 MySQL 表。Redis 使用 `ai:chat:{userId}:{threadId}` 作为键，保存经过裁剪的消息列表；`ai.history.ttl.hours` 控制过期时间，`ai.history.max.messages` 限制最大消息数。读取和写入都必须同时匹配当前用户和线程，不能只凭前端提交的 `threadId` 查询。模型、提示词版本、耗时和 token 用量可记录为运行日志，但不记录密码、openid、手机号或完整信用信息。

### 4.6 并发控制与事务边界

1. **入口锁**：所有整室/工位占用变更共用 `resv:lab:{labId}:{date}`。锁含唯一持有者令牌，等待时间默认 3 秒，Lua 按令牌释放；批量操作按 `labId、date` 排序加锁。
2. **数据库兜底**：事务内先确保整室日位图行存在，再对该行 `SELECT ... FOR UPDATE`。唯一键冲突时读取已有行重试。
3. **条件更新**：48 位掩码使用 MySQL 64 位以内位运算。占用更新同时校验版本号和 `(mask & reqMask) = 0`；影响行数不符则回滚。
4. **固定预约事务**：已通过预约单、正式座位分配、位图和初始日志在同一事务提交。任一失败整体回滚，锁在事务结束后释放。
5. **幂等与释放**：状态迁移使用 `WHERE id=? AND status=期望值`；释放前复核预约、正式座位分配及其 `time_mask`，避免迟到的任务影响后续占用。
6. **自动排期发布**：候选结果生成时不占资源。只有 `is_primary = true` 且第二阶段无未解决失败的主任务可进入发布；发布时按固定顺序加锁并重读最新占用，完成结果发布标记、预约状态、正式分配、位图和日志更新。失败回滚并保留待排期。

### 4.8 微信小程序与签到渠道设计

**小程序页面**：微信绑定页、实验室/工位查询页、预约提交页、我的预约页、扫码签到页、签退页、信用记录与申诉页、智能助手页（问答与预约草稿）。页面不暴露系统管理、资源维护、算法参数或实验管理入口。

**微信绑定流程**：

1. 小程序调用 `wx.login`，将临时凭证发送到后端。
2. 后端调用微信平台接口获得 openid，不接收或信任前端直接提交的 openid。
3. 未绑定账号时，学生输入学号和密码；后端验证账号状态及密码哈希。
4. 检查学号与 openid 的双向唯一绑定，写入 `sys_user` 后签发短期业务令牌。
5. 后续请求根据绑定关系识别学生；解绑或账号停用时令牌不得继续访问。

**核心接口设计**：

| 接口 | 用途 | 关键约束 |
|---|---|---|
| POST `/api/auth/wechat/login` | 微信临时凭证登录 | 后端换取 openid，返回绑定状态与短期令牌 |
| POST `/api/auth/wechat/bind` | 学号密码绑定微信 | 账号有效、密码正确、双向唯一绑定 |
| GET `/api/labs/{labId}/availability` | 查询实验室与工位可用性 | 只返回可公开资源信息 |
| POST `/api/reservations` | 提交固定或可调度需求 | 本人身份、规则与事务校验 |
| POST `/api/checkin/qr` | 小程序扫码签到 | 签名二维码、本人预约、同实验室、时间窗 |
| POST `/api/checkin/terminal` | 实验室电脑账号签到 | 有效终端会话、学号密码、本人预约、同实验室、时间窗 |
| POST `/api/checkin/{resvId}/checkout` | 签退 | 本人预约、当前使用中、剩余时间片计算 |

**终端账号签到流程**：

1. 系统管理员预置终端编码和终端凭证，终端与某一实验室绑定。浏览器仅保存 HttpOnly 终端会话，不保存学生密码。
2. 学生输入学号和密码。后端验证终端会话、账号有效状态、密码、失败锁定状态及当前签到窗口；不要求该账号已绑定微信。
3. 后端仅查询该学号在终端所属实验室的本人已通过预约。
4. 唯一符合预约直接签到；多条时返回仅限签到选择的短期凭证，学生选择后立即失效。
5. 签到成功后记录 `checkin_channel = TERMINAL_ACCOUNT`，清空表单和短期凭证并返回初始页。二维码渠道记录 `WECHAT_QR`。

签名二维码和账号密码均不能单独完全证明真实到场，因此终端绑定、预约归属、实验室匹配和时间窗必须同时成立；论文中不将扫码本身表述为绝对防代签。

### 4.9 智能预约助手设计

**图 4-14（`uml/oo-design/17_sequence_ai_assistant.puml`）** 给出完整调用过程。智能助手是独立 FastAPI 服务，不改变 Spring Boot 的业务事实地位，也不参与遗传排期算法。

#### 4.9.1 服务边界与调用链

1. 学生通过微信小程序或 Web 提交问题，Nginx 仅将 `/api/ai/**` 转发给 FastAPI，其他业务请求继续进入 Spring Boot。
2. FastAPI 通过 Spring Boot 身份接口验证业务令牌，取得服务器确认的 `userId` 和角色，不信任前端传入的用户身份。
3. 按 `userId + threadId` 从 Redis 读取并裁剪历史，加载系统提示词和白名单工具。
4. Agent 根据问题决定是否调用工具；工具通过内部 REST 访问 Spring Boot，并携带服务凭据和用户范围。
5. 模型只接收完成任务所需的脱敏数据，生成自然语言回答或结构化预约草稿。
6. Pydantic 校验输出结构，FastAPI 返回完整 JSON 或 SSE 流式片段，并追加本次对话到 Redis。
7. 草稿只回填普通预约表单。用户检查和确认后，前端调用既有 `POST /api/reservations`，由 Spring Boot 重新执行资格、双向冲突和事务校验。
8. 模型、平台或工具调用失败时返回可理解的降级信息，页面保留普通查询与预约入口。

#### 4.9.2 接口与工具

| 接口 | 调用端 | 返回与约束 |
|---|---|---|
| POST `/api/ai/chat/invoke` | 微信小程序 | 一次返回完整回答、可选草稿和引用信息；`message + threadId` 必须属于当前用户 |
| POST `/api/ai/chat/stream` | Web | `text/event-stream` 分片返回；以 `done` 或 `error` 结束，断线回退完整回答或普通表单 |
| GET `/api/ai/chat/history/{threadId}` | 小程序 / Web | 只返回当前用户自己的有限历史，禁止跨用户读取 |
| POST `/api/reservations` | 小程序 / Web | 草稿确认后的唯一预约写入入口，沿用既有业务校验和事务 |

| 工具 | 数据用途 | 权限边界 |
|---|---|---|
| `get_reservation_rules(labId?)` | 查询开放、时长、取消和签到规则 | 只读公开规则，不返回系统密钥或内部配置 |
| `query_lab_availability(labId, date, mode)` | 查询实验室与工位空闲情况 | 只读实时快照，回答时注明数据时间，不保证提交时仍空闲 |
| `query_my_reservations(userId, status?)` | 查询当前用户自己的预约 | `userId` 只能来自已验证令牌，禁止模型指定其他用户 |

不向 Agent 提供任意 SQL、文件读写、代码执行、创建/取消预约、签到、修改规则或发布排期工具。Spring Boot 内部工具接口与公开接口分别鉴权，并记录服务身份、用户范围、调用时间和结果状态。

#### 4.9.3 模型、提示词与结构化草稿

模型使用可配置的 OpenAI 兼容接口，通过 `ChatPromptTemplate` 固定“只回答实验室预约相关问题、工具事实优先、无法确定时明确说明”的系统提示。讲义中的模型工厂导入按本机验证结果写为：

```python
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent

llm = init_chat_model(
    model="deepseek-chat",
    model_provider="deepseek",
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com",
    temperature=0.2,
    max_tokens=1024,
    timeout=30,
)
agent = create_agent(llm, tools=[get_reservation_rules,
                                 query_lab_availability,
                                 query_my_reservations])
```

`os` 和三个工具在实现模块中定义，示例不包含任何真实密钥。`create_agent` 负责模型与工具编排；FastAPI 负责请求校验、身份验证、SSE 和异常边界，不把脚本直接暴露成无鉴权接口。

预约草稿 `ReservationDraft` 使用 Pydantic 定义：`labId`、`date`、`startTime`、`endTime`、`allocationMode`（默认 `FIXED`）、`reservationMode`、`seatCount` 和 `preferences`。`userId`、密码、openid、手机号和信用明细不进入草稿。结构合法不代表业务可预约，最终仍以 Spring Boot 校验结果为准。

#### 4.9.4 安全与降级

- 模型平台密钥仅存服务端环境变量；跨域使用来源白名单，不采用允许任意来源且携带凭据的配置。
- 工具输入和模型输出均校验，工具返回数据只作为事实来源，不执行其中包含的指令，降低提示词注入风险。
- 对话按键隔离、限制消息数并自动过期；历史接口同时校验 `userId` 和 `threadId`。
- 模型超时、限流、无效 JSON、工具无权限或平台不可用时，不回退到任意 SQL 或直接写入，而是返回普通表单。
- AI 生成内容标注“请核对后提交”；规则与空闲回答注明生成时间和数据来源，避免把模型推测当成实时事实。

### 4.10 物理设计

**图 4-7（`uml/oo-design/10_deployment.puml`）** 采用单机多进程部署：学生微信小程序、Web 浏览器和实验室签到电脑经 HTTPS 访问 Nginx；预约服务处理短事务，排期 Worker 执行计算，定时任务负责自动排期、主方案发布、爽约、到时结束与日统计。新增 `ai-service (Python + FastAPI + Uvicorn, :8000)`，仅访问 Redis、Spring Boot 内部只读接口和外部模型平台，不直连 MySQL。Nginx 按 `/api/ai/**` 与 `/api/**` 分流，8000 端口不直接暴露给公网。MySQL 与 Redis 可同机部署，备份文件异地或离线保存并定期验证可恢复性。

## 5 核心算法设计

### 5.1 固定 48 位掩码与冲突检测

```java
long reqMask  = buildMask(startTime, endTime);
long usedMask = bitmapDao.queryRoomMask(labId, date); // 无行返回 0L

boolean conflict = (reqMask & usedMask) != 0L;
long occupied = usedMask | reqMask;
long released = usedMask & ~reqMask;
```

| 方案 | 时间复杂度 | 空间与适用场景 | 本系统定位 |
|---|---|---|---|
| 内存区间逐条比较 | O(n) | 实现直观，适合小规模基线 | 实现，用于正确性对照 |
| 固定 48 位掩码 | 单次 O(1) | 每资源每日期一个 64 位字段，要求固定时间粒度 | 主实现 |
| 线段树 | O(log n) | 支持不规则区间与区间统计，实现成本较高 | 仅作比较分析 |

### 5.2 双粒度双向冲突判定

设 `Q` 为申请时间掩码，`R` 为整室掩码，`S[i]` 为第 i 个工位掩码：

- **工位申请**：先要求 `(Q & R) == 0`，再要求每个入选工位 `(Q & S[i]) == 0`，且工位状态可用、配置硬约束满足。
- **整室申请**：计算 `U = R OR S[0] OR ... OR S[m-1]`，要求 `(Q & U) == 0`。

```java
long roomMask = queryRoomMask(labId, date);
List<SeatMask> seatMasks = querySeatMasks(labId, date);

if (mode == ROOM) {
    long unionMask = roomMask;
    for (SeatMask seat : seatMasks) unionMask |= seat.mask();
    return (reqMask & unionMask) != 0L ? CONFLICT : AVAILABLE;
}

if ((reqMask & roomMask) != 0L) return CONFLICT;
List<Seat> candidates = activeSeats.stream()
    .filter(seat -> seat.meetsHardRequirement(request))
    .filter(seat -> (reqMask & seatMasks.maskOf(seat)) == 0L)
    .toList();
List<Seat> chosen = seatAllocator.allocate(candidates, request);
return chosen.size() == request.seatCount() ? AVAILABLE : CONFLICT;
```

全工位并集或候选扫描为 O(m)。一次 SQL 查询只描述 I/O 次数，不改变这一时间复杂度。

**落座算法**：先过滤不可用及冲突工位，再按区域和工位编号排序，优先选择满足硬约束且符合软偏好的同区域连续 K 个工位；无完整连续段时按配置满足度、靠窗偏好、工位编号选择 K 个并记录偏好错配。复杂度为 O(m log m + K)。

### 5.3 两阶段智能排期与自动发布

定时任务只处理 `SCHEDULABLE` 需求。第一阶段分配实验室与时段，第二阶段执行具体工位落座并验证方案。资源快照包含既有固定占用。

同一排期批次中，三套算法各自创建任务并共享数据集编号与快照。`schedule.primary.algorithm` 指定生产主算法，其他任务只用于实验对照。主任务第二阶段存在未解决失败时，本批不发布，需求保留待排期并进入后续批次；不自动改用对照任务结果。

| 算法 | 思路 | 复杂度口径 | 定位 |
|---|---|---|---|
| FCFS | 按申请时间排序，依次扫描候选资源槽 | O(N log N + N·M)，已排序时为 O(N·M) | 基线 |
| 贪心打分 | 按 `w1·紧急度 + w2·时长适配 + w3·历史信用 − w4·碎片惩罚` 排序并分配 | O(N log N + N·M) | 默认主方案 |
| 遗传算法 | 示例为种群 80、迭代 200 代；锦标赛选择（规模 3）+ 单点交叉(0.8) + 变异(0.05) + 精英保留(5%) + 贪心解注入，实际参数以实验记录为准 | 增量维护资源掩码时适应度评估为 O(G·P·N)，第二阶段另计 | 优化对比 |

遗传算法第一阶段适应度为：

`f = w1·预计分配成功率 + w2·预计资源利用率 − w3·时间碎片率 − w4·约束违反惩罚`

适应度不引用第二阶段实际工位偏好错配结果。每代通过修复或明确罚函数处理冲突染色体，复杂度结论以增量掩码评估实现为前提。

### 5.4 评价指标与实验设计

**算法对比统一五项指标**：

| 指标 | 统一口径 |
|---|---|
| 分配成功率 | 最终成功分配并落座的请求数 / 请求总数 |
| 平均工位利用率 | 已分配工位时间片 / 排期范围内可用工位时间片；整室预约按占用全部可用工位计 |
| 工位偏好错配率 | 未满足区域、靠窗等软偏好的已分配工位数 / 已分配工位总数；硬约束不满足属于分配失败 |
| 时间碎片率 | 无法组成最小预约时长的空闲时间片 / 总空闲时间片 |
| 两阶段求解耗时 | 分别记录第一阶段与第二阶段耗时，并给出总耗时 |

**落座失败率**是系统可靠性指标，定义为“已通过固定工位预约中缺少有效正式座位分配的预约数 / 已通过固定工位预约总数”，不计入五项算法对比指标。固定预约必须与完整座位分配同时提交。

| 实验维度 | 设置 |
|---|---|
| 数据规模 | N = 50 / 100 / 200 / 400，同时记录实验室、工位数、时段范围与需求分布 |
| 需求构成 | 整室与工位需求约 3:7，固定时长、人数和偏好由可复现的数据生成规则产生 |
| 重复次数 | FCFS/贪心的质量指标单次计算；GA 使用至少 10 个独立随机种子，报告均值和标准差；耗时测试统一预热与重复口径 |
| 公平性 | 各算法独立任务，共享数据集编号与资源快照，在同一台机器串行执行并使用相同第二阶段策略 |
| 数据留存 | 任务保存数据集编号、需求/资源快照、参数、随机种子、重复序号与运行环境；实验表保存五指标和分阶段耗时 |

重复运行用于降低随机波动并估计结果的变异性，不能替代独立验证。论文不预设遗传算法必然优于贪心，结论依据实测质量、耗时和波动得出。

### 6.2 答辩预判问题

1. **为什么用 48 位掩码？** 单个资源单次检测为 O(1)，字段固定且实现简单；全工位扫描成本按 O(m) 说明。
2. **整室和工位如何互斥？** 工位先查整室，整室检查整室与全部工位并集，两个方向在同一锁与事务边界内完成。
3. **预约何时生效？** 固定预约在资格、冲突和事务全部成功后直接进入已通过，任何部分失败都不生效。
4. **为什么小程序和电脑签到不需要两套规则？** 两个渠道只采集不同凭证，最终都由后端校验身份、本人预约、实验室和时间窗。
5. **电脑签到如何降低公共终端风险？** 终端与实验室绑定，密码哈希校验、失败限次、HTTPS、敏感日志脱敏，签到后清除表单且不保留完整学生会话。
6. **管理员只读如何实现？** 角色只分配查询权限，后端同时限制写接口，不能仅靠隐藏页面按钮。
7. **自动排期如何选择方案？** 主算法由配置指定，主任务合格才自动发布；其他算法只用于同快照实验，失败不在发布时临时换算法。
8. **实验如何复现？** 通过数据集、资源快照、参数、随机种子、重复序号和运行环境完整留存重建实验。
9. **为什么智能助手使用独立 FastAPI 服务？** LangChain 与 FastAPI 属 Python 生态，独立服务便于复用 Agent 和 SSE，同时避免替换稳定的 Java 预约核心；内部只读 REST 明确跨语言边界。
10. **AI 会不会直接修改预约或泄露其他用户数据？** 不会。Agent 只有白名单只读工具，会话按用户隔离，草稿必须经用户确认并由 Spring Boot 重新校验，敏感字段不发送到模型。
11. **当前电脑还缺哪些关键环境？** 实测需要另备 MySQL 8.0、补 Redis 和一个模型 API Key；正式发布还需微信凭据，其余主要运行库已验证可用。

### 6.3 测试与验收设计

| 场景 | 操作 | 必须满足的结果 |
|---|---|---|
| 固定预约自动生效 | 提交合法整室或工位申请 | 预约、正式分配、位图与日志同时提交，状态为已通过 |

| 批量提交 | 同批包含全部可用与部分冲突两种数据 | 可用批次全部生效；冲突批次整批回滚 |

| 公共终端安全 | 连续失败、签到成功、选择超时、检查日志与会话 | 触发限次锁定；成功或超时清除短期凭证；无完整学生会话和敏感日志 |

| 自动排期发布 | 主任务合格、主任务第二阶段失败、快照过期 | 合格主方案自动发布；失败回滚并保留待排期；对照任务不占资源 |
| 管理员只读 | 实验室管理员调用查询和写接口 | 查询按权限返回，所有写接口被拒绝，页面无操作入口 |

| AI 会话与工具权限 | 使用他人 threadId、要求任意 SQL 或调用写接口 | 全部拒绝，无跨用户数据、无直接数据库访问和预约写入 |
| AI 输出与草稿 | 模拟无效 JSON、过期空闲数据和草稿冲突 | 无效输出被拒绝；草稿确认时由 Spring Boot 重检，冲突不生效 |
| AI 失败降级 | 模拟模型超时、限流、SSE 中断和平台不可用 | 普通预约和签到继续可用，回退完整回答或普通表单，不写入业务数据 |
| AI 隐私 | 检查工具输入、模型上下文和运行日志 | 不包含密码、openid、手机号、完整信用记录或其他用户数据 |
