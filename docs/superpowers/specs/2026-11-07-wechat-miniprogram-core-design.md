# 微信小程序端核心闭环设计

> 日期：2026-11-07
> 状态：已与用户确认架构、页面原型、数据流、安全与验收方向
> 关联文档：`doc/系统分析与设计说明书.md`、`doc/工位级预约细化设计说明.md`

## 1. 目标与范围

在现有 Spring Boot 后端和 Vue Web 端基础上，新增微信原生小程序，完成学生个人预约与到场使用的核心闭环：

1. 微信登录、首次学号密码绑定，以及无微信凭据时的开发账号登录。
2. 实验室、开放规则、整室占用与工位余量查询。
3. 固定时空预约和可调度需求提交。
4. 我的预约、预约详情、取消预约。
5. 微信扫码签到和提前签退。

首期为个人预约，不包含教师课程批次、信用记录与申诉、AI 助手、资源管理、排期实验管理或统计分析。除签到码内容接口外，不改造 Web 页面。正式发布、微信服务器域名配置和真机发布审核不属于本期交付。

## 2. 技术路线

采用 **微信原生小程序 + TypeScript**，在项目根目录新增独立的 `miniprogram/` 工程。

选择理由：

- 直接使用 `wx.login`、`wx.request`、`wx.scanCode` 和小程序生命周期，避免跨端框架带来的编译与兼容成本。
- 与既有系统设计一致，不引入 React 或新的跨端运行时。
- Web 端的 Vue 组件、Element Plus、Vue Router 和 Pinia 不能直接复用；仅复用业务类型语义、接口契约和视觉语言。

不引入 UI 组件库。使用原生组件、全局设计变量和少量页面共享组件，保持首屏与安装包精简。

## 3. 应用结构

### 3.1 页面

底部三个标签页：

- **首页**：问候、下一场预约、扫码签到入口、实验室预约与我的预约快捷入口、近期预约。
- **实验室**：实验室选择、日期选择、整室/工位模式、30 分钟时间片、规则摘要和预约入口。
- **我的**：当前账号、角色、开发登录标识、我的预约入口和退出登录。

非标签页面：

- 登录页：真实微信登录；仅开发配置展示账号密码登录。
- 微信绑定页：学号、密码和一次性绑定凭证。
- 预约提交页：预约方式、粒度、人数、工位数、用途和工位偏好；根据固定/可调度模式显示对应字段。
- 预约记录页：状态筛选、分页加载、详情、取消、签到和签退入口。
- 预约详情页：正式时段、实验室、座位、用途、签到签退信息及当前可执行操作。

### 3.2 模块边界

- `api/`：Promise 化的 `wx.request` 封装、接口函数和响应类型。
- `auth/`：业务令牌与用户信息存取、登录状态恢复、退出登录。
- `config/`：API 地址与是否显示开发登录；不包含 AppSecret、二维码签名密钥或固定业务令牌。
- `components/`：时间片选择器、预约卡片、加载/空状态等确有复用需求的组件。
- `utils/`：本地日期格式、状态文案和连续时间片选择等纯逻辑。
- `pages/`：页面编排，不承载位图、签到窗口或预约资格等业务判定。

使用页面数据与简单认证状态模块，不引入 Pinia。业务 JWT 和脱敏用户信息可保存在微信本地存储；密码、openid、绑定凭证和扫码原文不持久化。

## 4. 视觉与交互

延续 Web 端 LabSpace 的视觉语言：

- 主色 `#3867e8`，正文 `#18243a`，背景 `#f4f7fb`，成功色 `#159b72`。
- 白色圆角卡片、清晰的状态标签、较大的主要操作按钮。
- 首页优先展示下一场预约和扫码签到，不复刻桌面数据看板。
- 移动端用可点选的连续时间片替代表格和位图原值；位图掩码仍由后端使用，不在页面展示。
- 预约记录使用卡片和状态筛选，不使用横向滚动大表格。

已确认的浏览器原型保存在项目 `.superpowers/brainstorm/` 会话目录中，仅用于设计参考，不进入小程序运行代码。

### 4.1 时间片选择

- 使用 `GET /api/labs/{labId}/availability` 返回的 48 个时间片及当日开放规则。
- 第一次点选设置起点，第二次点选设置终点；自动交换反向选择。
- 非连续、超出开放时间、整室已占用或无可用工位的区间不能进入提交页，并说明原因。
- 整室模式以 `roomOccupied` 判断；工位模式以 `availableSeatCount` 判断当前快照。
- 前端选择仅是输入辅助，最终可约性以提交时后端校验为准。

## 5. 认证与账号绑定

### 5.1 微信登录

`POST /api/auth/wechat/login`

请求：`{ "code": "wx.login 返回的临时 code" }`。

后端通过 HTTPS 调用微信 `jscode2session`，从服务端配置读取 AppID 和 AppSecret。不得信任前端直接提交的 openid，也不得把 AppSecret 或 openid 返回给小程序。

响应分为两种：

- 已绑定：`{ "bound": true, "token": "业务 JWT", "user": "现有 UserView" }`。
- 未绑定：`{ "bound": false, "bindTicket": "一次性随机凭证", "expiresIn": 300 }`。

绑定凭证是至少 256 位随机值，后端在 Redis 保存其与 openid 的映射，有效期 5 分钟。未绑定响应不包含业务 JWT，不能访问受保护业务接口。

### 5.2 学号绑定

`POST /api/auth/wechat/bind`

请求：`{ "bindTicket": "...", "account": "学号", "password": "密码" }`。

处理规则：

1. 校验绑定凭证存在且未过期。
2. 复用现有 BCrypt 密码校验和账号有效状态检查。
3. 检查该学号未绑定其他 openid，该 openid 也未绑定其他学号。
4. 在事务中写入现有 `sys_user.wechat_openid` 和 `wechat_bind_time`，数据库唯一约束作为并发兜底。
5. 绑定成功后使凭证失效，签发与 Web 登录相同的业务 JWT 和 UserView。

错误密码允许在凭证有效期内重试，但连续失败达到 5 次后使该绑定凭证失效。过期、已使用、重复绑定或账号停用均失败，不记录密码、openid 或 AppSecret 日志。无需新增数据库表或字段。

### 5.3 开发登录与身份恢复

- 开发配置显示“开发登录”，调用现有 `POST /api/auth/login`，账号密码仅用于当次请求。
- 不增加模拟 openid、免登录或后端认证绕过接口。
- 启动时恢复本地 JWT 和用户信息，并调用 `GET /api/auth/me` 验证；401 清除本地身份并返回登录页。
- 普通网络失败保留本地身份并展示重试，不把离线误判为退出登录。
- 退出登录只清除小程序本地身份；现有无状态 JWT 服务端保持不变。

## 6. 预约数据流

复用现有接口及 `ApiResponse` 包装：

- `GET /api/labs`
- `GET /api/labs/{labId}/rules`
- `GET /api/labs/{labId}/availability?date=YYYY-MM-DD`
- `POST /api/reservations`
- `GET /api/reservations/my`
- `GET /api/reservations/{reservationId}`
- `POST /api/reservations/{reservationId}/cancel`

首页读取当前用户已通过、使用中和待排期预约，优先展示使用中的预约，其次展示最近的已通过预约。记录页按状态筛选并分页加载，详情页使用详情接口刷新正式分配结果。

固定预约和可调度需求沿用现有 `CreateReservationRequest`，不新增小程序专用业务规则。提交期间禁用按钮；成功后刷新记录和可用性。发生 409 时保留表单内容，提示时段或资源已变化，并允许返回刷新。

## 7. 二维码签到与签退

### 7.1 签到码内容

签到码文本采用以下逻辑格式：

`labspace://checkin?v=1&labId={labId}&signature={base64url-hmac-sha256}`

签名输入为规范化的版本和实验室 ID，密钥通过 `WECHAT_CHECKIN_QR_SECRET` 提供给后端，长度至少 32 字节，不与微信 AppSecret 复用。验签使用常量时间比较，拒绝未知版本、额外参数、非法实验室和错误签名。

`GET /api/admin/resources/labs/{labId}/checkin-code` 仅允许系统管理员调用，返回待编码为二维码的文本。本期不引入二维码图片生成依赖，也不新增 Web 管理页面；开发工具可模拟扫描该文本，部署时可用二维码工具制作实验室实体码。

签名码用于证明二维码由系统签发，不单独证明真实到场。签到仍必须满足本人预约、同实验室、预约状态和签到时间窗。

### 7.2 扫码签到

`POST /api/checkin/qr`

请求：`{ "reservationId": 123, "content": "wx.scanCode 返回的原文" }`。

处理流程：

1. 从业务 JWT 获取用户 ID，角色要求与现有个人签到一致。
2. 解析并验证二维码，取得后端认可的实验室 ID。
3. 查询预约并取得对应实验室、日期锁。
4. 复用 `ReservationCheckinTransactionService` 的本人、实验室、状态和时间窗判断。
5. 将原签到事务泛化为接收签到渠道：终端调用仍写 `TERMINAL_ACCOUNT`，二维码调用写 `WECHAT_QR`，日志文案按渠道区分。
6. 返回最新 ReservationView 和 `alreadyCheckedIn` 标志。

已处于使用中的本人预约重复扫码按已签到处理，不重复写签到事实或状态日志。所有锁在 `finally` 中释放，终端签到现有接口和行为保持不变。

### 7.3 提前签退

继续使用 `POST /api/checkin/{reservationId}/checkout`。增加可选渠道请求体；小程序传 `WECHAT_QR`，缺省保持 `WEB_ACCOUNT`，因此现有 Web 请求无需修改。后端只允许白名单渠道值，不接受任意渠道文本。其余状态迁移、剩余完整时间片释放和日志规则不变。

## 8. 请求与异常处理

请求层统一完成：

- 拼接 API 地址和 `Authorization: Bearer` 头。
- 解包 `code = 0` 的响应，其他响应转换为包含 HTTP 状态、业务码和用户提示的错误。
- 20 秒超时、网络错误提示和防重复提交。
- 401 清理身份并跳回登录页；403 显示无权限；409 保留用户输入并引导刷新。

页面必须为异步操作提供加载、空数据、失败重试和成功反馈。取消预约、提前签退需要二次确认；取消原因最长 500 字。扫码取消或识别失败不改变预约状态。

微信 code 无效时提示重新登录；微信平台超时或不可用时返回可重试的降级提示，不回退到无认证访问。开发登录只在开发配置中出现，正式构建不得显示。

## 9. 配置与秘密边界

后端新增配置项：

- `WECHAT_APP_ID`：微信小程序 AppID。
- `WECHAT_APP_SECRET`：仅后端使用的 AppSecret。
- `WECHAT_CHECKIN_QR_SECRET`：仅后端使用的签到码 HMAC 密钥。

AppID 可写入开发者工具项目配置，但两个秘密均不得进入小程序包、Web 包、文档或仓库。本地与测试配置可使用明确标注的非生产测试值；生产缺失秘密时应明确报告微信能力未配置，不能静默切换为开发登录。

## 10. 测试与验收

### 10.1 后端自动化

沿用现有 Spring Boot 测试体系，覆盖：

- 微信登录成功、未绑定、无效 code 和微信平台异常。
- 正确绑定、错误密码、停用账号、学号/openid 双向唯一冲突、凭证过期和重复使用。
- 正确二维码、伪造签名、非法内容、错误实验室、非本人预约、非已通过状态和窗口外签到。
- 重复签到幂等、签到渠道与日志正确、终端签到回归、锁释放。
- 微信签退渠道、缺省 Web 渠道和非法渠道值。
- 签到码内容接口仅系统管理员可访问。

### 10.2 小程序自动化与编译

- 类型检查和小程序开发者工具编译无错误。
- 纯逻辑测试覆盖连续时间片选择、反向选择、无效区间、日期与状态显示。
- 请求层测试覆盖响应解包、401、网络失败和错误保留策略。
- 认证状态测试覆盖恢复、退出和开发/正式入口配置。

### 10.3 端到端验收

在本地后端和微信开发者工具中验证。签到场景使用独立的测试实验室与测试规则，明确允许当日预约、覆盖当前时间并放宽最少提前天数；不得修改正常演示规则来迁就测试：

1. 开发账号登录 → 实验室与规则查询 → 固定预约 → 查看正式分配 → 取消。
2. 开发账号登录 → 在签到测试实验室创建临近时段预约 → 模拟扫描有效签到码 → 使用中 → 微信渠道签退。
3. 伪造二维码、错误实验室、非本人预约和窗口外请求均被拒绝。
4. 现有 Web 登录、预约、终端签到和签退回归通过。

真实 `wx.login` 与真机扫码只有在有效 AppID/AppSecret、HTTPS 域名和真机环境齐备后才能验收；缺少这些条件时只能声明开发者工具及模拟微信网关测试通过，不能声称正式微信链路已实测。

## 11. 成功标准

本期完成时，小程序工程可在微信开发者工具打开，用户能够通过真实后端完成个人预约、取消、扫码签到与签退闭环；微信绑定和二维码安全规则有自动化测试，现有 Web 与终端功能无回归。未配置的正式微信平台凭据不阻塞开发闭环，但必须作为上线前事项明确保留。
